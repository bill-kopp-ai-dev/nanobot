## 1. Escopo fechado e critério de aceite

**Decisões vinculantes:** B14/B23 dão às tools MCP Docker acesso amplo de leitura/escrita a **arquivos** do host por padrão ("a máquina é do agente"), sem filtro por projeto/workspace, mas excluem o plano de controle Docker e o estado/credenciais da capability; B15 exige as oito famílias de operação abaixo; B16 escolhe broker Python próprio em processo/container separado (socket só nele); B17 põe a configuração em `config.json` sob `tools.mcpDocker`; B18 cria a credencial `operator-admin`; B19 fixa estados, CAS, backup e compensação; B20 restringe a primeira fase a imagens já presentes; B21 determina CI Linux-only Ubuntu 22.04 + Arch; B22/B23 mantêm Engine 27.x e daemon rootful, mas substituem o broker systemd por sidecar Docker e o mount recursivo irrestrito por bind raiz não recursivo com coberturas; B24 fecha o gate F0 e explicita a aceitação do risco **indireto** (R/W no restante do host; token lido pelo processo gateway) sem alegar isolamento total — o re-aceite do risco medido em F1 e a aceitação final em F5/deploy continuam obrigatórios. Nenhum controle aqui garante isolamento contra escalada **indireta** por escrita no host ou exploração da API broker a partir do gateway. Não há aprovação por tool nem perfis Local/Global. Todas as tools descobertas são habilitadas por padrão; desabilitação individual e desativação do servidor valem para **toda** chamada.

| Família (B15) | Comportamento exigido na primeira versão utilizável |
| --- | --- |
| 1. Instalar | Inspecionar imagem presente, persistir identidade imutável, ativar globalmente por padrão e descobrir tools; se não conectar, reter registro/erro sem publicar tools. |
| 2. Configurar host | Editar mounts/rede/env com revisão e prévia do acesso efetivo; reiniciar quando a mudança exigir recriar container. |
| 3. Tools | Desabilitar/reabilitar pelo nome bruto e `server_id`, inclusive após rediscovery e com wrappers/sessões em cache. |
| 4. Servidor | Desativar/reativar; desativação revoga imediatamente todas as tools, sem excluir configuração. |
| 5. Atualizar imagem | Pré-validar identidade, fazer backup e compensar falhas; preservar `toolsDisabled` das tools que ainda existem; novas tools entram habilitadas. |
| 6. Reiniciar | Ciclo do container/conexão sem alterar imagem ou configuração. |
| 7. Excluir registro | Confirmar digitando `server_id`, fazer backup, revogar e remover registro/container gerenciado; não remover imagem, volumes nem paths do host. |
| 8. Persistente | Start/stop somente se `configurations[id].persistent: true` (opt-in; default `false`), com estado e perdas transitórias mostrados. |

**Aceite do produto:** as oito famílias funcionam pela página **e** API de domínio, em duas imagens MCP reais, no Compose do VPS; gateway sem socket/CLI Docker, MCP sem acesso direto comprovado ao daemon pelas montagens permitidas, risco **indireto** medido e explicitamente aceito, política de host verificada, persistência `.percival`, estados/auditoria/recuperação observáveis, autenticação administrativa e gates da seção 7 aprovados. F3 (página de leitura) não é entrega funcional. F5 e o aceite do operador antecedem qualquer alegação de prontidão; o plano não autoriza tag, release, repositório público nem publicação.

**Fora desta primeira entrega:** migração automática de MCPs genéricos, perfis por projeto, catálogo OCI remoto, pulls implícitos, assinatura de terceiros, OAuth compartilhado, criação de outra SPA. `source.type: "repository"` fica reservado e **rejeitado** até uma fase posterior; não incluir controles de catálogo ainda inoperantes na UI de v1.

## 2. Fronteiras, deployment e viabilidade

```text
VPS / Docker Compose
WebUI --WebSocket autenticado--> container gateway Python (nanobot; sem socket/CLI)
                                 | mesmo namespace de rede; HTTP 127.0.0.1 + token
                                 v
                         container broker Python (UID dedicado + GID docker;
                         socket montado somente aqui; porta não publicada)
                                 | /usr/bin/docker --> daemon rootful no VPS
                                 v
                         containers MCP: /host R/W para arquivos da raiz
                         (bind-recursive=disabled + coberturas do control plane)
Persistência: pasta .percival no host --> /home/nanobot/.nanobot no gateway
```

- **Gateway:** dono exclusivo da intenção persistida, máquina de estados, gate por chamada, CAS, autenticação WebUI e auditoria. WebUI/TUI não executam Docker. `tools.mcpServers` genéricos conservam sua semântica; nomes de tools gerenciadas precisam de namespace estável e tratamento determinístico de colisão, sem dar acesso acidental à tool genérica de mesmo nome. `ExecTool`, shell e agente não recebem montagem do socket nem CLI/credenciais **do daemon**; compartilham porém o namespace de rede do broker. A garantia de que não possam obter **acesso indireto via API/token do broker** depende de prova específica e pode exigir aceite de risco, conforme B23 — não confundir com ausência de socket.
- **Broker (B16/B23):** sidecar Python próprio em Compose, processo/container distinto, `network_mode: service:nanobot-gateway` para partilhar **somente o namespace de rede** e permitir bind a `127.0.0.1` dentro desse namespace; nenhum `ports` no broker. Único container com bind do socket (caminho real a verificar no VPS) e `/usr/bin/docker` na sua imagem; UID não-root dedicado e `group_add` com **GID numérico do socket no VPS**, sem incluir `nanobot` nesse grupo. Não reutilizar o `x-common-config` do gateway para o broker; sem mount do estado do gateway inteiro. `cap_drop: ALL`, `no-new-privileges`, raiz da imagem read-only e paths de escrita mínimos onde compatível. O grupo docker equivale a root no host; a antiga unit systemd/usuário host de B22 deixa de ser deployment canônico (B23), não é requisito de F5. Reinício/recriação do gateway pode exigir recriar sidecar para entrar no novo namespace; health/reconnect devem ser ensaiados.
- **Protocolo:** MCP Streamable HTTP e endpoints administrativos tipados do broker em `127.0.0.1` **do namespace compartilhado**, com segredo estático rotacionável; validar em cada chamada administrativa e MCP, sem endpoint que aceite comando Docker/flags arbitrárias. Não publicar porta do broker para host/bridge; outros processos no namespace do gateway (incluindo exec tool) alcançam esse loopback, portanto autenticação e ausência de operações genéricas são essenciais. Testar armazenamento/rotação de token e restrição de acesso do shell; **não afirmar** que a exec tool jamais conseguirá acessar a API equivalente se puder ler o segredo do gateway. Rotação e timeouts devem ser especificados/validados em F1/F2. Não substituir o transporte por Unix socket sem revisão de B16. [Compose `network_mode: service:`](https://docs.docker.com/reference/compose-file/services/#network_mode) define a topologia candidata; a prova local de dois containers não substitui o ensaio no VPS.
- **Engine:** invocar CLI em `/usr/bin/docker`; `DOCKER_BIN`/`DOCKER_HOST` podem sobrescrever **somente** com validação do caminho/endpoint e da política de deployment. `docker --version` verifica **CLI**, não daemon: checar também `docker version` (Server.Version), conectividade/permissões e compatibilidade com a linha 27.x definida em B22; falha deixa `broker-not-ready`, sem publicar tools. Confirmar em F0 a disponibilidade e manutenção da linha 27.x no ambiente alvo, sem pressupor que a expressão "LTS" seja uma propriedade comprovada do Engine. Não passar comandos pelo shell; usar argumentos tipados, timeouts, captura e redação de erros.
- **Mount default (B14/B22 revisados por B23):** `--mount type=bind,src=/,dst=/host,bind-recursive=disabled` **R/W**, sem bind direto de `/run`, `/proc`, `/sys`, `/dev`, nem de sockets; `rprivate` e sem privilégios extras. [Docker documenta](https://docs.docker.com/engine/storage/bind-mounts/#recursive-mounts) que `bind-recursive=disabled` omite submounts, não que exclua diretórios no filesystem raiz. Cobrir com tmpfs ou montagem inerte dentro do container MCP **o Docker data-root efetivo** (p.ex. `/host/var/lib/docker`) e a **pasta persistente `.percival` do VPS** (e outros paths do daemon/token descobertos); paths de exclusão canônicos e aliases resolvidos/inspecionados antes de instalar/spawn, sem confiar em lista fixa de nomes. O broker deve verificar `docker info`, mount table e `docker inspect` e falhar fechado se caminho protegido não puder ser coberto. `configurations[id].mounts` pode **reduzir** o acesso, nunca reintroduzir um path protegido via bind custom, symlink, proc ou configuração de rede. Confirmar na imagem real que R/W para arquivos comuns ainda funciona; o teste F0 usou mount **read-only**. Excluir o estado do gateway da visão MCP reduz vazamento direto, mas `/:/host` R/W ainda pode permitir escalada indireta por modificar `/etc`, binários, unidades, cron, home ou caminhos de controle não previstos. Não prometer isolamento total nem sigilo do host; se a proteção bloquear uso necessário no VPS, pedir exceção **específica e auditável** ao operador, não remover coberturas silenciosamente.
- **Persistência Docker no VPS:** o deployment atual monta `~/.nanobot` no caminho interno `/home/nanobot/.nanobot`. O alvo será **uma pasta `.percival` do host** com path absoluto configurado (ex.: `/srv/percival/.percival`), montada nesse caminho interno **sem renomear o aplicativo agora**. `config.json`, operador, audit, backups e transitions ficam no mesmo volume persistido (`runtime_data_dir`), com ownership/mode adequados a UID 1000; broker guarda somente seu estado operacional mínimo, com token acessível ao gateway, sem copiar o `config.json` inteiro. Planejar migração com backup, validação de permissões, rollback e restart, sem mover/renomear automaticamente o estado existente; excluir **o path real da pasta persistente** do mount MCP. Cobrir igualmente qualquer volume/host path que armazene token operacional. Volume Docker tem backing store no data-root: proteger também esse backing store. Prova de persistência exige recriar gateway e broker e reconciliar containers MCP sem perda de registros, audit e credenciais.
- **Rede e segredos:** mostrar mount/rede/env efetivos e egress antes da instalação. `secret` em `config.json` é texto claro (B17), embora redigido na API; **mesmo com coberturas** não prometer sigilo do host a um MCP com amplo R/W. Também não colocar token de broker em env inspecionável sem validar exposição; credenciais no gateway e API acessível ao gateway criam risco indireto de exec. Não adicionar `tools.ssrfWhitelist` amplo para liberar MCP privado: validar destinos e redirects ou usar transporte privado testado. Backups/credenciais/audit precisam de diretórios e permissões restritos.

## 3. Contratos de domínio e recuperação

### Configuração, imagens e tools

- `tools.mcpDocker` em `config.json`: `schemaVersion: 1`, `revision` da seção e revisão por `server_id`, inventário `servers`, configurações separadas por ID, `toolsDisabled`, `allow_remote_admin: false` por default. Reutilizar `save_config`/`_write_text_atomic`. **Não criar** `registry.json` nem lock de filesystem; serializar todas as escritas do arquivo por um writer do gateway, além dos locks por `server_id` e CAS, inclusive quando outros domínios salvarem `config.json`. Na primeira criação, garantir modo `0600` e diretório privado: `_write_text_atomic` só preserva o modo **se o arquivo já existir**. Validar schema/migração de versões futuras e rollback de config inválida.
- B20 Fase 1: `local-image` = ID local completo `sha256:<64 hex>`; `pinned-image` = `nome@sha256:<64 hex>` presente localmente, validado por RepoDigest. ID de imagem e RepoDigest são identificadores distintos; `docker image inspect` valida o que será executado e `docker run --pull=never` impede pull implícito. Para testar `pinned-image` a partir de fixtures construídas localmente (que normalmente não têm RepoDigest), fornecer registry local isolado/manifesto pinado ou fixture verificável apropriada; não tratar uma tag ou ID como RepoDigest. Atualização usa um **segundo digest real** por fixture, sem pull em produção nessa fase.
- `env` tipado: `plain` persiste/exibe literal; `secret` persiste literal mas leituras mostram sentinel `_REDACTED_MCP_ENV_SECRET` e mask hint do padrão de `providers.<name>.api_key` (`abc1••••xyz9`); resubmissão do sentinel preserva o valor anterior somente no campo já existente. `reference` persiste `"${VAR}"` e é resolvido do **ambiente do broker** no spawn, falhando fechado se ausente. O gateway precisa transmitir temporariamente ao broker o valor de `secret` necessário para criar o container; a promessa é **não expor em respostas, audit, logs ou armazenamento próprio do broker**, e não "nunca enviar ao broker". `docker inspect`/env do container e Docker CLI também podem revelar valores a quem controla o daemon; testar a superfície real. Mounts de segredo expõem só paths na UI, nunca o conteúdo.
- Para cada `server_id`, publicar `tools/list - toolsDisabled` se ativado e conectado; descobertas novas entram por default. Conferir ativação/disable **antes de toda chamada** em qualquer sessão/canal, mesmo em wrapper previamente descoberto ou durante reconnect; distinguir resources/prompts de tools sem liberar estes últimos por acidente. Testar colisão com `tools.mcpServers` e remoção de tool na atualização.

### Operações, estados e durabilidade

- B19 mantém intenção, observação Docker e conectividade MCP **separadas**: `installed`, `configured-disabled`, `starting`, `running`, `restarting`, `updating`, `stopped-persistent`, `pending-broker`, `image-missing`, `config-invalid`, `updating-failed`; observações indisponíveis viram `unknown`, não `running`. Registrar transições válidas, respostas 400/409 a ações inválidas/conflitos e contrato para queda do broker; `stdio` sob demanda pode estar parado normalmente.
- Operações são idempotentes por `server_id` + revisão/idempotency key onde apropriado, com lock por servidor e CAS do arquivo. A transição de config + Docker **não é transação física**: "atômico" em update significa compensação observável. Pré-validar novo digest, salvar backup de `servers[i]` + `configurations[id]` e manifesto, marcar operação, criar/substituir container, redescobrir e só então confirmar; falha restaura intenção anterior, preserva revisão monotônica, registra `updating-failed` e informa se a restauração do container também falhou. Não prometer voltar automaticamente ao estado `running` se o daemon estiver offline.
- Antes de `update-image` e `exclude`, backup em `runtime_data_dir/mcp-docker/backups/<ISO-ts>-<id>-<uuid>/`; restore CLI inicial `restore-f1` foi ensaiado em F1; `nanobot mcp-docker restore <backup_dir>` usa o writer real em F2, valida manifesto, prévia, CAS/conflito e não sobrescreve outro servidor. UI de restore em F5. `exclude` revoga primeiro, remove container gerenciado sem `docker rm -v`, preserva imagem/volumes/paths e registra identificadores dos volumes anônimos para eventual recuperação; não afirmar que uma referência de volume anônimo fica automaticamente recuperável sem metadados.
- F1 é **protótipo**, sem garantia de recuperação após crash. A capacidade não é pronta para uso até F5: journal por servidor em `runtime_data_dir/mcp-docker/transitions/<id>.json` com `preparing`/`committed`/`failed`, `backup_path` e reconciliação de estado real no startup; recovery testa interrupção em cada fronteira (antes/depois de persistir, parar, criar, descobrir e excluir). Rollback automático só quando for possível verificar a imagem/container antigos e CAS; caso contrário manter pendente, gate fechado e instrução de intervenção. Audit append-only `runtime_data_dir/mcp-docker/audit.jsonl` (modo `0600`) com `started` → `committed`/`failed`, revisão/correlation ID e diff **redigido**, sem segredos/payloads de tools.

### Superfície WebUI e autenticação

- Rotas allowlisted sob `/api/settings/mcp-docker/*`: **uma leitura** `list` e **11 ações de mutação** `install`, `configure`, `disable-tool`, `enable-tool`, `activate`, `deactivate`, `update-image`, `restart`, `start`, `stop`, `exclude`. São oito **famílias** de operação (B15), não oito endpoints; bootstrap de credencial e restore têm contratos adicionais próprios. Chamadas de domínio usadas pela CLI seguem a mesma validação/estado.
- O código atual envia mutações WebUI por **WebSocket autenticado**, não por POST HTTP arbitrário. O `Authorization` da requisição WebSocket já carrega o bearer WebUI; não é possível transportar simultaneamente dois Bearer independentes no mesmo cabeçalho. A credencial `operator-admin` (B18) deve viajar em um **campo tipado separado do payload da ação WebSocket** (ou cabeçalho distinto se um transporte HTTP autenticado separado for projetado), ser retirada antes do domínio/audit e validada no servidor para **cada** mutação; acesso HTTP direto à rota de mutação continua 405. Testar WebUI bearer/credencial em combinação, 401 para credencial ausente/incorreta e 403 para origem remota com `allow_remote_admin=false`, inclusive via proxy; não confiar em uma flag `local_browser` enviada pelo cliente.
- Senha definida pelo operador; hash em `runtime_data_dir/mcp-docker/operator.json` modo `0600` (não em `config.json`): `hashlib.scrypt` N=2**15, r=8, p=1, salt aleatório 16 bytes, dklen=32, formato `scrypt$N$r$p$<salt-b64>$<hash-b64>`, `hmac.compare_digest`. CLI `operator-init`/`operator-rotate` e UI de setup/rotação. `GET .../operator-bootstrap` só para navegador loopback autenticado e devolve **somente status**. O primeiro setup **não pode exigir uma credencial que ainda não existe**: desenhar a exceção de bootstrap uma única vez, limitada ao operador local autenticado (ou CLI) e testá-la contra corrida/proxy; rotação posterior exige credencial válida ou recuperação via CLI no VPS. Senha fica somente na memória da página (Redux), é limpa em logout/desconexão e nunca em storage persistente, URL, logs ou payload para broker. Para CI, gerar senha/token efêmeros no job para testar fluxos negativos/positivos; "sem secrets em CI" significa sem `secrets.*` externos, não dispensar testes de auth.
- F3 exibe lista, identidade de imagem, mount/rede metadata, intenção, estados separados, tools, último resultado/audit redigido, loading/empty/error; não expõe valor real de `secret`, `reference` resolvida, conteúdo de mount de segredo ou senha. F4 implementa formulário Mount/Network/Env com semáforo verde/amarelo/cinza, prévia de diff sem segredos e confirmação digitada para **aumento** de escopo (B22/B23); redução consciente é explícita, sem alterar silenciosamente o default de acesso amplo a arquivos do host **com exclusões obrigatórias**. A UI não permite remover coberturas do plano de controle por operação ordinária. Mostrar resultado efetivo após salvar, não apenas valores solicitados; update, exclude, restore e persistência têm prévia e confirmação proporcional.

## 4. Fases, dependências e gates

**F0 — Inventário e desenho verificável** (agente; operador aprova deployment). **F0 fechado** em 2026-10-07 via B24: desenho/topologia (B23) executado em disposable env local via `scripts/percival-f0-validate.sh` (bind-recursive=disabled + tmpfs no data-root + filtro server-side do broker) com 11 asserts verdes; script de inventário do VPS (`scripts/percival-vps-inventory.sh`) pronto; operador aceita formalmente o risco **indireto** documentado em §7.2.  O **inventário real do VPS permanece pendente** (Client/Server 27.x, GID numérico do socket no VPS, alias do data-root, candidato `.percival`, portas publicadas) — `scripts/percival-vps-inventory.sh` deve ser executado **antes do F5/deploy canônico**, com divergências exigindo nova decisão.  Mudança de Engine/isolamento se 27.x ou proteções forem inviáveis em produção exige decisão nova. F0 não instala nada no VPS por pressuposição.

**F1 — Protótipo em ambiente descartável** (depende de F0). Subir gateway **em Docker** + sidecar broker Python com Docker CLI 27.x, namespace de rede compartilhado e auth no loopback; somente broker monta o socket, gateway/exec não. Ensaiar raiz R/W não recursiva + coberturas no **daemon host do VPS**; verificar também paths do estado `.percival` e do token. Buildar `percival-weather-mcp` v0.9.0 (9 tools) e `percival-osm` v0.5.0 (30+ tools) com digest registrado e versões de fonte. Exercitar em **ambas** as fixtures: `initialize`, `tools/list`, uma chamada real sem segredo, oito famílias B15, falha de update com segundo digest real + compensação, start/stop opt-in, desconexão/reconexão, colisões/concorrência e medição de cold start/latência. Provar acesso R/W autorizado a arquivo de teste no host e tentativas negativas de conexão direta ao daemon **do container MCP (inclusive imagem root), gateway e agente/exec** via sockets/aliases, proc, data-root, TCP, mounts custom e token broker; registrar separadamente qualquer possibilidade indireta via shell e R/W no host sem executar escalada destrutiva. Recriar gateway/sidecar e verificar persistência de `config.json`/audit em `.percival`; `restore` CLI inicial com backup legível, sem alegação de crash recovery. **Gate:** relatório reproduzível (SHA, versões, mounts/rotas, imagens/digests, configuração redigida, testes, resultados e limites) e **aceite expresso do risco residual pelo operador**; falha de cobertura direta não permite seguir com esse perfil, mas risco indireto conhecido pode ser aceito deliberadamente sem alegar isolamento completo. Mock, página de listagem ou `docker ps` não satisfazem F1.

**Resultado F1 local (B25):** a prova foi separada em topologia completa no Engine 29.7.2 local e compatibilidade Client+Server 27.5.1 em dind isolado (duas chamadas reais, mount e negativas UID 0). A exigência original de topologia **inteira** no daemon 27.x **do VPS** continua como gate de F5/deploy, de acordo com B24 e o pedido explícito do operador de validar o VPS depois; nenhuma prova 29.x foi rotulada como 27.x. No host local `/home` foi incluído seletivamente e o arquivo aprovado foi lido e escrito com UID 1000, com masks e negações comprovadas. Outros submounts, política dinâmica, permissões dos UIDs padrão das imagens, restore transacional e writer real permanecem F2–F5, sem reivindicar acesso total/isolamento em qualquer VPS.

**F2 — Backend, broker e testes de contrato** (depende de F1). **Fechada localmente em 2026-10-07**; evidência e limitações em [relatório F2](../reports/2026-10-07-mcp-docker-f2-progress.md). Schema e serviço de domínio, single-writer/CAS, env, auth, rotas, backup/audit e restore CLI usam writer real. ## 5. Matriz de riscos e evidência exigida

| Risco / conflito | Controle e evidência para fechar |
| --- | --- |
| Raiz R/W expõe socket, Docker data-root ou segredo por aliases/submounts/custom mounts | Bind não recursivo e coberturas derivadas do host, sem `docker.sock` em gateway/exec/MCP; F1 tenta conectar ao daemon do MCP e gateway e verificar volumes de estado. Falha direta fecha gate; acesso indireto residual por escrita host não é chamado de isolamento e precisa de aceite específico. |
| Gateway e broker em containers com loopback compartilhado | `network_mode: service:nanobot-gateway`, somente broker tem socket; testar autenticação MCP/admin, portas publicadas, reconexão após recriação do gateway e que exec não recebe CLI/socket (token/API indiretos podem ser alcançáveis). |
| Estado persistido `.percival` difere do atual `~/.nanobot` | Bind host explícito para caminho interno atual, backup/cópia controlada e validação de mode, persistência após recriação e rollback; excluir backing path do mount MCP e não apagar estado ao executar `compose down`. |
| CLI compatível com daemon ausente/inacessível | Checar Client e Server.Version, `docker info`/permissões, caminho absoluto e timeout; erro `broker-not-ready`, ferramentas não publicadas. |
| Dois tokens bearer disputam `Authorization`; bootstrap sem senha prévia | Teste WebSocket autenticado com campo administrativo tipado, rejeição HTTP direto, bootstrap local único/CLI e rotação; logs/redaction. |
| Update/exclude interrompidos e escritores concorrentes perdem config | Single-writer para todo `config.json`, CAS monotônico, backups, journal em F5 e reconciliação; injetar crash em cada passo e verificar estado Docker e config, sem alegar atomicidade distribuída. |
| Imagem/digest incorretos, fixture externa indisponível no CI | Checar ID vs RepoDigest, `--pull=never`, segundo digest real para update, snapshot de fonte/licença; testes contra imagem local e referência por digest de registry de teste. |
| Secrets redigidos na UI ainda expostos por host/daemon | Permissões `0600` na criação e reload, proteção do path `.percival` e Docker data-root, payloads/logs redigidos; aceitar que R/W no restante do host ainda permite escalada indireta e acesso a outros segredos do host. |
| Desabilitação bypassada por cache/namespace de tools | Gate por chamada em todos canais, wrappers obsoletos, colidir nomes de MCP genérico/gerenciado e revalidar durante reconnect. |
| CI Linux-only diverge do deploy real; regressão flakey | Fixar versões/Arch por data, cache de pacman e revisão trimestral, isolamento `docker:dind`/cleanup, timeout e diagnóstico de falha; não esconder falha por retry automático; ensaio na topologia de VPS. |
| Escopo de release excede evidência | Gates B12 em SHA candidato, limitações conhecidas, licença/proveniência/segredos e sign-off B13; nenhuma tag/publicação implícita. |
