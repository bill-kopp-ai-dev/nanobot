## 1. Escopo fechado e critério de aceite

**Decisões vinculantes:** B14 dá às tools MCP Docker acesso de leitura/escrita ao host inteiro por padrão ("a máquina é do agente"), sem filtro por projeto/workspace; B15 exige as oito famílias de operação abaixo; B16 escolhe broker Python próprio em processo separado; B17 põe a configuração em `config.json` sob `tools.mcpDocker`; B18 cria a credencial `operator-admin`; B19 fixa estados, CAS, backup e compensação; B20 restringe a primeira fase a imagens já presentes; B21 determina CI Linux-only Ubuntu 22.04 + Arch; B22 fixa Docker Engine 27.x, daemon rootful, usuário `docker-broker`, mount default `/:/host` R/W e UI de redução consciente. Não há aprovação por tool nem perfis Local/Global. Todas as tools descobertas são habilitadas por padrão; desabilitação individual e desativação do servidor valem para **toda** chamada.

| Família (B15) | Comportamento exigido na primeira versão utilizável |
| --- | --- |
| 1. Instalar | Inspecionar imagem presente, persistir identidade imutável, ativar globalmente por padrão e descobrir tools; se não conectar, reter registro/erro sem publicar tools. |
| 2. Configurar host | Editar mounts/rede/env com revisão e prévia do acesso efetivo; reiniciar quando a mudança exigir recriar container. |
| 3. Tools | Desabilitar/reabilitar pelo nome bruto e `server_id`, inclusive após rediscovery e com wrappers/sessões em cache. |
| 4. Servidor | Desativar/reativar; desativação revoga imediatamente todas as tools, sem excluir configuração. |
| 5. Atualizar imagem | Pré-validar identidade, fazer backup e compensar falhas; preservar `toolsDisabled` das tools que ainda existem; novas tools entram habilitadas. |
| 6. Reiniciar | Ciclo do container/conexão sem alterar imagem ou configuração. |
| 7. Excluir registro | Confirmar digitando `server_id`, fazer backup, revogar e remover registro/container gerenciado; não remover imagem, volumes nem paths do host. |
| 8. Persistente | Start/stop somente se `configurations[id].persistent: true` (opt-in; default `false`), com estado e perdas transitórias mostrados. |

**Aceite do produto:** as oito famílias funcionam pela página **e** API de domínio, em duas imagens MCP reais, com gateway sem acesso ao daemon, política de host verificada, estados/auditoria/recuperação observáveis, autenticação administrativa e gates da seção 7 aprovados. F3 (página de leitura) não é entrega funcional. F5 e o aceite do operador antecedem qualquer alegação de prontidão; o plano não autoriza tag, release, repositório público nem publicação.

**Fora desta primeira entrega:** migração automática de MCPs genéricos, perfis por projeto, catálogo OCI remoto, pulls implícitos, assinatura de terceiros, OAuth compartilhado, criação de outra SPA. `source.type: "repository"` fica reservado e **rejeitado** até uma fase posterior; não incluir controles de catálogo ainda inoperantes na UI de v1.

## 2. Fronteiras, deployment e viabilidade

```text
WebUI (cliente) --WebSocket autenticado--> gateway Python (domínio, config, auth, gate)
                                         --MCP Streamable HTTP autenticado em 127.0.0.1-->
                              broker Python `nanobot-mcp-broker` (runtime Docker)
                                         --CLI /usr/bin/docker--> daemon rootful
                                                    |--> containers MCP --> mount /:/host R/W
```

- **Gateway:** dono exclusivo da intenção persistida, máquina de estados, gate por chamada, CAS, autenticação WebUI e auditoria. WebUI/TUI não executam Docker. `tools.mcpServers` genéricos conservam sua semântica; nomes de tools gerenciadas precisam de namespace estável e tratamento determinístico de colisão, sem dar acesso acidental à tool genérica de mesmo nome. `ExecTool`, shell e agente não recebem socket, credenciais do daemon nem APIs equivalentes.
- **Broker (B16/B22):** processo distinto sob usuário de sistema `docker-broker` (nologin, sem sudo, home `/var/lib/docker-broker`, membro do grupo `docker`); somente ele fala com o daemon. Unit `nanobot-mcp-broker.service` com `NoNewPrivileges`, `ProtectSystem=strict`, `PrivateDevices`, `ReadWritePaths=/var/lib/docker-broker`, `RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6` e `MemoryDenyWriteExecute=true`. O gateway continua sob `nanobot`, fora do grupo `docker`. A pertença ao grupo `docker` equivale, na prática, a privilégio de root sobre o host: hardening do processo não elimina esse risco.
- **Protocolo:** MCP Streamable HTTP e endpoints administrativos tipados do broker em `127.0.0.1`, com segredo compartilhado estático rotacionável; validar segredo em todas as chamadas administrativas e de MCP, sem endpoint que aceite comando Docker/flags arbitrárias. Token estático por si só não comprova identidade de ambos os processos; proteger armazenamento, permissões, origem, bind e vazamento em logs. Não substituir o transporte por Unix socket sem revisão explícita de B16. Um gateway em container não compartilha automaticamente o `127.0.0.1` do host: F0/F1 devem demonstrar a topologia real (host/namespace/proxy local autenticado), mantendo gateway sem socket e broker não exposto externamente; se não for possível, parar e replanejar.
- **Engine:** invocar CLI em `/usr/bin/docker`; `DOCKER_BIN`/`DOCKER_HOST` podem sobrescrever **somente** com validação do caminho/endpoint e da política de deployment. `docker --version` verifica **CLI**, não daemon: checar também `docker version` (Server.Version), conectividade/permissões e compatibilidade com a linha 27.x definida em B22; falha deixa `broker-not-ready`, sem publicar tools. Confirmar em F0 a disponibilidade e manutenção da linha 27.x no ambiente alvo, sem pressupor que a expressão "LTS" seja uma propriedade comprovada do Engine. Não passar comandos pelo shell; usar argumentos tipados, timeouts, captura e redação de erros.
- **Mount default (B14/B22):** `/:/host` R/W, com `configurations[id].mounts` para redução consciente. Isso também expõe por padrão `config.json`, segredos do host e possivelmente `/host/var/run/docker.sock` (ou sockets por symlink, `/run` e `/proc`): **não afirmar que o agente está isolado do daemon só porque o gateway não monta o socket**. F0 mapeia aliases e o desenho de bloqueio; F1 tenta acessá-los a partir da própria tool/container. Só prosseguir se conseguir preservar o acesso amplo decidido em B14 **sem** dar ao agente/exec tool acesso ao daemon, conforme B14/B16, ou levar o conflito material ao operador para nova decisão. Sem prova, não há gate de isolamento aprovado. Rootful e acesso R/W a `/` mantêm risco residual de leitura/mutação do host mesmo com o socket bloqueado.
- **Rede e segredos:** mostrar mount/rede/env efetivos e impacto de egress antes da instalação. `secret` em `config.json` é texto claro (B17), embora redigido na API; não prometer confidencialidade do host contra um MCP que recebe `/:/host`. Não adicionar `tools.ssrfWhitelist` amplo para liberar MCP privado: validar destinos e redirects ou usar transporte privado testado. Backups/credenciais/audit precisam de diretórios e permissões restritos.

## 3. Contratos de domínio e recuperação

### Configuração, imagens e tools

- `tools.mcpDocker` em `config.json`: `schemaVersion: 1`, `revision` da seção e revisão por `server_id`, inventário `servers`, configurações separadas por ID, `toolsDisabled`, `allow_remote_admin: false` por default. Reutilizar `save_config`/`_write_text_atomic`. **Não criar** `registry.json` nem lock de filesystem; serializar todas as escritas do arquivo por um writer do gateway, além dos locks por `server_id` e CAS, inclusive quando outros domínios salvarem `config.json`. Na primeira criação, garantir modo `0600` e diretório privado: `_write_text_atomic` só preserva o modo **se o arquivo já existir**. Validar schema/migração de versões futuras e rollback de config inválida.
- B20 Fase 1: `local-image` = ID local completo `sha256:<64 hex>`; `pinned-image` = `nome@sha256:<64 hex>` presente localmente, validado por RepoDigest. ID de imagem e RepoDigest são identificadores distintos; `docker image inspect` valida o que será executado e `docker run --pull=never` impede pull implícito. Para testar `pinned-image` a partir de fixtures construídas localmente (que normalmente não têm RepoDigest), fornecer registry local isolado/manifesto pinado ou fixture verificável apropriada; não tratar uma tag ou ID como RepoDigest. Atualização usa um **segundo digest real** por fixture, sem pull em produção nessa fase.
- `env` tipado: `plain` persiste/exibe literal; `secret` persiste literal mas leituras mostram sentinel `_REDACTED_MCP_ENV_SECRET` e mask hint do padrão de `providers.<name>.api_key` (`abc1••••xyz9`); resubmissão do sentinel preserva o valor anterior somente no campo já existente. `reference` persiste `"${VAR}"` e é resolvido do **ambiente do broker** no spawn, falhando fechado se ausente. O gateway precisa transmitir temporariamente ao broker o valor de `secret` necessário para criar o container; a promessa é **não expor em respostas, audit, logs ou armazenamento próprio do broker**, e não "nunca enviar ao broker". `docker inspect`/env do container e Docker CLI também podem revelar valores a quem controla o daemon; testar a superfície real. Mounts de segredo expõem só paths na UI, nunca o conteúdo.
- Para cada `server_id`, publicar `tools/list - toolsDisabled` se ativado e conectado; descobertas novas entram por default. Conferir ativação/disable **antes de toda chamada** em qualquer sessão/canal, mesmo em wrapper previamente descoberto ou durante reconnect; distinguir resources/prompts de tools sem liberar estes últimos por acidente. Testar colisão com `tools.mcpServers` e remoção de tool na atualização.

### Operações, estados e durabilidade

- B19 mantém intenção, observação Docker e conectividade MCP **separadas**: `installed`, `configured-disabled`, `starting`, `running`, `restarting`, `updating`, `stopped-persistent`, `pending-broker`, `image-missing`, `config-invalid`, `updating-failed`; observações indisponíveis viram `unknown`, não `running`. Registrar transições válidas, respostas 400/409 a ações inválidas/conflitos e contrato para queda do broker; `stdio` sob demanda pode estar parado normalmente.
- Operações são idempotentes por `server_id` + revisão/idempotency key onde apropriado, com lock por servidor e CAS do arquivo. A transição de config + Docker **não é transação física**: "atômico" em update significa compensação observável. Pré-validar novo digest, salvar backup de `servers[i]` + `configurations[id]` e manifesto, marcar operação, criar/substituir container, redescobrir e só então confirmar; falha restaura intenção anterior, preserva revisão monotônica, registra `updating-failed` e informa se a restauração do container também falhou. Não prometer voltar automaticamente ao estado `running` se o daemon estiver offline.
- Antes de `update-image` e `exclude`, backup em `runtime_data_dir/mcp-docker/backups/<ISO-ts>-<id>-<uuid>/`; restore CLI `nanobot mcp-docker restore <backup_dir>` em F1, com validação do manifesto, prévia, CAS/conflito e sem sobrescrever outro servidor. UI de restore em F5. `exclude` revoga primeiro, remove container gerenciado sem `docker rm -v`, preserva imagem/volumes/paths e registra identificadores dos volumes anônimos para eventual recuperação; não afirmar que uma referência de volume anônimo fica automaticamente recuperável sem metadados.
- F1 é **protótipo**, sem garantia de recuperação após crash. A capacidade não é pronta para uso até F5: journal por servidor em `runtime_data_dir/mcp-docker/transitions/<id>.json` com `preparing`/`committed`/`failed`, `backup_path` e reconciliação de estado real no startup; recovery testa interrupção em cada fronteira (antes/depois de persistir, parar, criar, descobrir e excluir). Rollback automático só quando for possível verificar a imagem/container antigos e CAS; caso contrário manter pendente, gate fechado e instrução de intervenção. Audit append-only `runtime_data_dir/mcp-docker/audit.jsonl` (modo `0600`) com `started` → `committed`/`failed`, revisão/correlation ID e diff **redigido**, sem segredos/payloads de tools.

### Superfície WebUI e autenticação

- Rotas allowlisted sob `/api/settings/mcp-docker/*`: **uma leitura** `list` e **11 ações de mutação** `install`, `configure`, `disable-tool`, `enable-tool`, `activate`, `deactivate`, `update-image`, `restart`, `start`, `stop`, `exclude`. São oito **famílias** de operação (B15), não oito endpoints; bootstrap de credencial e restore têm contratos adicionais próprios. Chamadas de domínio usadas pela CLI seguem a mesma validação/estado.
- O código atual envia mutações WebUI por **WebSocket autenticado**, não por POST HTTP arbitrário. O `Authorization` da requisição WebSocket já carrega o bearer WebUI; não é possível transportar simultaneamente dois Bearer independentes no mesmo cabeçalho. A credencial `operator-admin` (B18) deve viajar em um **campo tipado separado do payload da ação WebSocket** (ou cabeçalho distinto se um transporte HTTP autenticado separado for projetado), ser retirada antes do domínio/audit e validada no servidor para **cada** mutação; acesso HTTP direto à rota de mutação continua 405. Testar WebUI bearer/credencial em combinação, 401 para credencial ausente/incorreta e 403 para origem remota com `allow_remote_admin=false`, inclusive via proxy; não confiar em uma flag `local_browser` enviada pelo cliente.
- Senha definida pelo operador; hash em `runtime_data_dir/mcp-docker/operator.json` modo `0600` (não em `config.json`): `hashlib.scrypt` N=2**15, r=8, p=1, salt aleatório 16 bytes, dklen=32, formato `scrypt$N$r$p$<salt-b64>$<hash-b64>`, `hmac.compare_digest`. CLI `operator-init`/`operator-rotate` e UI de setup/rotação. `GET .../operator-bootstrap` só para navegador loopback autenticado e devolve **somente status**. O primeiro setup **não pode exigir uma credencial que ainda não existe**: desenhar a exceção de bootstrap uma única vez, limitada ao operador local autenticado (ou CLI) e testá-la contra corrida/proxy; rotação posterior exige credencial válida ou recuperação via CLI no VPS. Senha fica somente na memória da página (Redux), é limpa em logout/desconexão e nunca em storage persistente, URL, logs ou payload para broker. Para CI, gerar senha/token efêmeros no job para testar fluxos negativos/positivos; "sem secrets em CI" significa sem `secrets.*` externos, não dispensar testes de auth.
- F3 exibe lista, identidade de imagem, mount/rede metadata, intenção, estados separados, tools, último resultado/audit redigido, loading/empty/error; não expõe valor real de `secret`, `reference` resolvida, conteúdo de mount de segredo ou senha. F4 implementa formulário Mount/Network/Env com semáforo verde/amarelo/cinza, prévia de diff sem segredos e confirmação digitada para **aumento** de escopo (B22); redução consciente é explícita, sem alterar silenciosamente o default `/:/host`. Mostrar resultado efetivo após salvar, não apenas valores solicitados; update, exclude, restore e persistência têm prévia e confirmação proporcional.

## 4. Fases, dependências e gates

**F0 — Inventário e desenho verificável** (agente; operador aprova deployment). Levantar host/Compose, rede e namespaces entre gateway e broker, socket/aliases do Docker, mounts efetivos e paths sensíveis, usuário `nanobot`, `MCPProvider`, WebSocket/auth, reload de config e escritor único. Fixar CLI/daemon 27.x realmente disponíveis, Python SDK MCP, política de timeout/rotação, licença/revisão das fixtures externas e como torná-las reproduzíveis no CI (sem depender de `/home/bill/Projects/...`). Entregar mapa de ameaças com teste de alcance do daemon através de `/:/host`, contrato de transporte e conjunto mínimo de testes de viabilidade. **Gate:** operador aceita a topologia e a prova proposta; se B14 e a proibição de socket para o agente forem incompatíveis na topologia alvo, reabrir a decisão antes de iniciar F1. F0 não instala nada no VPS por pressuposição.

**F1 — Protótipo em ambiente descartável** (depende de F0). Subir broker Python com Docker CLI 27.x, autenticação no loopback, gateway sem acesso ao daemon; buildar `percival-weather-mcp` v0.9.0 (9 tools) e `percival-osm` v0.5.0 (30+ tools) com digest registrado e versões de fonte. Exercitar em **ambas** as fixtures: `initialize`, `tools/list`, uma chamada real sem segredo, oito famílias B15, falha de update com segundo digest real + compensação, start/stop opt-in, desconexão/reconexão, colisões/concorrência e medição de cold start/latência. Provar com tentativas reais (do gateway, agente/exec e container MCP) o isolamento do daemon, inclusive acesso pelo mount raiz, symlinks e caminhos alternativos. `restore` CLI inicial com backup legível, sem alegação de crash recovery. **Gate:** relatório reproduzível (SHA de cada fonte, imagens/digests, versões, configuração redigida, comandos/testes, resultados e limites) e decisão explícita do operador seguir/replanejar; mock, páginas de listagem ou testes apenas de `docker ps` não satisfazem F1.

**F2 — Backend, broker e testes de contrato** (depende de F1). Implementar schema e serviço de domínio, single-writer `save_config`, lock/CAS, configuração/env, auth `operator-admin`, rotas tipadas, backup/audit, transporte MCP/gate em todos os caminhos, broker Docker CLI e verificação de prontidão. Implementar as oito famílias no gateway/broker; não declarar prontidão de update/exclude frente a crash até F5. Reconciliar CI herdado Linux-only (remover jobs Windows/macOS pertinentes, preservar cobertura Python/WebUI/TUI) e introduzir job `mcp-broker` smoke com fixtures reproduzíveis. **Gate:** testes unitários/de integração para todas as operações, estados válidos/inválidos, CAS, redaction, fallback com broker offline, autorização local/remota, persistência/mode, compatibilidade de MCP genérico e isolamento; smoke real no Docker quando o código da capability mudar.

**F3 — Página observacional** (depende da leitura F2). Integrar rota `/mcp-containers` à WebUI existente, sidebar e link Apps/MCP; lista/detalhe/histórico, estados Docker vs MCP, acessibilidade e payloads redigidos. Planejar setup de senha sem pedir a senha novamente após cada render; não ativar mutações falsas. **Gate:** UI + gateway real em estados vazio, conectado, imagem ausente, broker indisponível e erro; nenhuma resposta de leitura divulga segredos ou credenciais.

**F4 — Gestão pela página** (depende de F2/F3 e provas F1). Conectar as oito famílias a ações tipadas; formulário Mount/Network/Env, status de escopo e confirmações B22/B19; restore ainda disponível via CLI. Tratar 401/403/409, re-fetch após conflito, bloqueio imediato de tools, atualização com rollback e resultados verificáveis. **Gate:** fluxo completo sem edição manual de JSON, com duas fixtures, confirmação `server_id`, round-trip de `secret` (valor → máscara → sentinel → mesmo valor), setup/rotação de credencial, outro servidor não afetado e prova de mount/rede efetivos. A primeira versão utilizável inclui F4, mas prontidão requer F5.

**F5 — Recuperação, CI e prontidão** (depende de F4). Implementar journal e reconciliação de crash, UI de restore, deployment systemd do broker sob `docker-broker`, documentação de instalação/rollback e observabilidade. Completar CI B21: PR lint/typecheck/pytest em Ubuntu 22.04 e Arch pinado (container sobre runner Ubuntu); smoke `mcp-broker` em PR **quando tocar MCP Docker**, tudo em merge para `main`, regressão noturna com fixtures buildadas no momento. Python 3.12 (mínimo, Arch + Ubuntu) e 3.14 (latest/coverage, Ubuntu); Bun 1.3.6 WebUI/1.3.13 TUI; Engine 27.x; pin Arch `archlinux:base-<YYYYMMDD>` com revisão trimestral. Eliminar `windows_process`, matriz TUI Windows e targets darwin/win do `tui-release.yml`; manter **ambos** os artefatos Linux se ainda suportados (o workflow atual inclui `linux-arm64` e `linux-x64`), não reduzir automaticamente para `linux-x64` sem decisão. Ensaiar em VPS/Compose alvo e registrar limitações. **Gate:** recuperação após crash em cada fronteira, duas fixtures e oito famílias combinadas, isolamento por mount, resultado no SHA candidato e aceite expresso do operador; sem prometer release se falhar.

**Caminho crítico:** F0 (topologia e viabilidade B14/B16/B22) → F1 (prova broker e isolamento) → F2 (domínio e contratos) → F3/F4 (UI) → F5 (recovery e gate de integração). Trabalho visual e fixtures podem correr em paralelo após F0; F4 depende de mutações validadas. Estimar horas/recursos após F1; dependências externas são Engine/daemon, acesso a duas fontes de fixture e runner Docker para integração. Catálogo OCI compartilhado com Positronic é **Fase 2 posterior**, dependente de catálogo publicado e nova decisão de implementação; não é F2/F3 deste plano.

## 5. Matriz de riscos e evidência exigida

| Risco / conflito | Controle e evidência para fechar |
| --- | --- |
| `/:/host` dá acesso ao socket e a segredos, apesar de gateway isolado | F0 inventaria paths reais e aliases; F1 tenta conectar ao daemon do container MCP e via agente/exec. Bloquear gate e escalar se não houver desenho viável compatível com B14/B16. Documentar acesso residual ao host; UI não mascara esse risco. |
| Gateway em container não alcança broker em loopback do host | Diagrama de namespaces + prova MCP e admin em topologia alvo; não publicar broker na interface pública nem conectar gateway ao socket para contornar. |
| CLI compatível com daemon ausente/inacessível | Checar Client e Server.Version, `docker info`/permissões, caminho absoluto e timeout; erro `broker-not-ready`, ferramentas não publicadas. |
| Dois tokens bearer disputam `Authorization`; bootstrap sem senha prévia | Teste WebSocket autenticado com campo administrativo tipado, rejeição HTTP direto, bootstrap local único/CLI e rotação; logs/redaction. |
| Update/exclude interrompidos e escritores concorrentes perdem config | Single-writer para todo `config.json`, CAS monotônico, backups, journal em F5 e reconciliação; injetar crash em cada passo e verificar estado Docker e config, sem alegar atomicidade distribuída. |
| Imagem/digest incorretos, fixture externa indisponível no CI | Checar ID vs RepoDigest, `--pull=never`, segundo digest real para update, snapshot de fonte/licença; testes contra imagem local e referência por digest de registry de teste. |
| Secrets redigidos na UI ainda expostos por host/daemon | Permissões `0600` na criação e reload, política de diretórios, payloads/logs redigidos; documentar que MCP com mount raiz pode ler arquivos de config/credenciais. |
| Desabilitação bypassada por cache/namespace de tools | Gate por chamada em todos canais, wrappers obsoletos, colidir nomes de MCP genérico/gerenciado e revalidar durante reconnect. |
| CI Linux-only diverge do deploy real; regressão flakey | Fixar versões/Arch por data, cache de pacman e revisão trimestral, isolamento `docker:dind`/cleanup, timeout e diagnóstico de falha; não esconder falha por retry automático; ensaio na topologia de VPS. |
| Escopo de release excede evidência | Gates B12 em SHA candidato, limitações conhecidas, licença/proveniência/segredos e sign-off B13; nenhuma tag/publicação implícita. |
